# VoxCPM Narrate 実用化プラン

作成日: 2026-09-16。未コミットの変更を含む現在のソースを対象とする。今回は計画作成のみ。

## 目標と前提

日本語ナレーションを作る個人が、台本を取り込み、短く試聴し、全編を生成し、気になる箇所だけ直して納品できるローカル制作アプリにする。

初期対象は単一ユーザー・単一マシン。既存の Python / FastAPI / HTML・CSS・JavaScript と CLI を活かす。音声合成はローカル、外部 LLM 評価は任意。複数人向けホスティング、認証基盤、別 TTS エンジン、フロント全面刷新は初期範囲に含めない。

最初の実用リリースはフェーズ 0〜2。フェーズ 3〜4 は実音声での検証結果を踏まえて進める。

## 目指す制作体験

1. 過去の制作を開く、または新規作成。
2. 台本を入力・取り込み。読み上げ本文、分割、読み方、間を事前確認。
3. 参照音声と話し方を選び、選択範囲の短い試聴を生成。
4. 全編生成。進行中も完成部分を聴けて、中断・再開できる。
5. 気になる箇所を修正。元音声と候補を比較し、採用または元に戻す。
6. 全体を連続試聴し、WAV と必要な制作データを書き出す。

画面は「制作一覧」と「制作画面」の二つを基本とする。制作画面は台本・セグメント一覧、選択箇所の編集、常設プレイヤーを中心に構成。生成パラメータや LLM 設定は詳細設定へ移し、通常操作では「試聴」「全編生成」「再生成」「採用」「書き出し」を使う。「パターンB」は「音声を聴いて改善提案」に変更する。

## 現状の根拠

以下は静的確認と限定的な再現確認。実モデルの合成性能、音質、OpenRouter の実接続は未検証。

- **再現済み:** `console.py:38` の `log_error()` は `Console.print(stderr=True)` により TypeError になる。CLI の入力エラーだけでなく、バックグラウンド例外処理にも影響する。
- **再現済み:** `extract.py` の分割は句点のない長文に上限を保証しない。80文字の入力が `max_chars=20` でも1セグメントのままになる。
- **コード上で確認:** `web/static/app.js:516` はファイル選択済みだと編集欄より元ファイルを送信する。読み込み後の台本編集が生成に反映されない。
- **コード上で確認:** 同ファイルの `mergeSegmentView()` はサーバー値で編集状態を上書きし、`renderSegments()` は一覧 DOM を作り直す。ポーリング時の編集保持・フォーカス保持に問題がある。
- **コード上で確認:** `web/app.py:356` は再生成成功前に manifest を更新し、成功候補は既存 WAV に直接書き込む。失敗時の本文・音声の不一致と、手動再生成の履歴消失を防ぐ必要がある。
- **コード上で確認:** `web/jobs.py` はジョブ情報をメモリだけに保持する。出力ファイルが残っても、サーバー再起動後に同じ制作を API から復元する仕組みがない。
- **コード上で確認:** セグメント再生成ごとにモデルをロードする。遅延への影響量は計測が必要。
- **コード上で確認:** テキスト LLM 評価の通信失敗が 0.5 点として扱われる。音声評価モデルの可否は固定一覧依存で、動的モデル一覧との整合がない。
- **コード上で確認:** WAV 参照入力は元パスをそのまま利用するため、CLI の後続改善が期待する run 内の参照音声保存と一致しない場合がある。
- **確認範囲:** 専用のテスト群は見当たらない。Python 17ファイルの構文、サンプル Markdown / SSML の解析、CLI dry-run は通過済み。

## フェーズ 0 — 編集と失敗処理の不具合を止める

優先度 P0。概算 1〜2 人日。依存なし。

実施内容:

- エラー出力を修正し、例外ログが失敗してもジョブを確実に失敗状態へ移す。
- 取り込みファイルを編集欄に展開し、生成時は現在の編集内容を入力の正とする。
- 編集中の値とサーバー確定値を分離。ポーリングは状態だけ差分更新し、カーソル位置を維持する。
- アップロードを固定の別名で保存し、同名の台本と参照音声が上書きし合わないようにする。
- 存在しないセグメント、空本文、生成条件の範囲外値を受付時に検証。再試行成功時に古いエラーを消去できるようにする。
- 候補を別ファイルへ生成してから確定する暫定フローを導入し、失敗時は元本文・元 WAV を保持する。永続的な履歴はフェーズ 1 で完成させる。

完了条件:

- ファイル取り込み後に1文字変更すると、その変更後の本文が合成へ渡る。
- 連続した状態更新でも入力中の本文・選択範囲・フォーカスが維持される。
- モデル例外を注入してもジョブが実行中のまま残らず、直前の採用音声と本文が一致して残る。

## フェーズ 1 — 制作データを保存し、中断から復帰できるようにする

優先度 P0。概算 3〜5 人日。フェーズ 0 の後。

実施内容:

- SQLite に制作・セグメント・生成候補・操作状態を保存。大きな音声ファイルは従来どおりファイルシステムに置く。
- 元台本、修正文、話し方、実際に使用した seed、モデル ID / 取得可能な revision、生成条件、参照音声のコピーとハッシュを記録。API キーは制作データに含めない。
- セグメントの版は不変にし、採用版への参照だけ変更する。合成した全体音声にも入力となった採用版一覧を持たせる。
- 候補書き込み → 音声検証 → 永続化 → 採用版変更の順に処理。途中停止では未採用ファイルを回収し、旧採用版を保持する。
- 明示的なキューを設け、生成・再生成の状態遷移を共通化する。要求 ID と版番号で二重実行・古い結果の採用を防ぐ。
- キャンセルはセグメント境界で協調停止。再起動時の実行中ジョブは「中断」に変え、ユーザー操作で未完了部分だけ再開する。
- 制作一覧・制作詳細取得・再開操作を追加し、URL から制作を再表示できるようにする。既存 manifest と WAV は読み取り確認後に取り込み、元データを保持する。

完了条件:

- 5セグメント生成後にプロセスを終了・再起動し、完了5件を再生成せず残りを再開できる。
- 同一箇所に複数操作が来ても、古い評価や生成結果が新しい採用版を上書きしない。
- 候補保存中・採用処理中・全体結合中の各中断から、最後に確定した本文と音声を復元できる。
- 参照音声の元ファイルを移動しても、保存済み制作から再生成できる。

## フェーズ 2 — 試聴しながら仕上げる制作画面にする

優先度 P1。概算 3〜5 人日。フェーズ 1 の保存・版管理を利用。

実施内容:

- Web でも Markdown・プレーンテキスト・SSML を扱う。既存パーサーを共有し、XML エラーは位置と修正の手がかりを表示する。
- 合成前に分割プレビューを出す。句点 → 読点 → 安全な長さでの分割を行い、長い1文の扱いを明示する。
- 読み上げ本文、読み方、話し方、セグメント前の間を別々に編集する。台本を大きく変更した際は再分割の差分と、再生成が必要な箇所を提示する。
- 「選択箇所を試聴」から始められるようにする。参照音声なしの既存機能も Web に公開する。
- セグメントを連続再生し、現在位置を追従表示。元音声・候補の比較、採用、元に戻すを用意する。
- 「要確認」「未生成」「採用済み」の絞り込みと、選択部分のみの再生成を追加する。
- キーボード操作、編集欄ラベル、フォーカス表示、画面幅への追従を整える。エラーは alert だけに頼らず該当操作のそばで示す。

完了条件:

- ユーザーが台本取り込み → 短い試聴 → 全編生成 → 1箇所修正 → 比較・採用 → 書き出しをターミナルなしで完了できる。
- 再読み込みで編集状態と採用版を復元できる。
- 100セグメントの台本でも、状態更新中に編集・再生操作が妨げられない。

**ここを最初の実用リリースとする。** 追加の品質機能より先に、実案件を1本仕上げて制作上の不便を確認する。

## フェーズ 3 — 品質評価を信頼できる補助機能にする

優先度 P1。概算 3〜5 人日。フェーズ 1〜2 の版比較・採用操作が前提。

実施内容:

- 「音響チェック」「文字起こし照合」「音声を聴いて改善提案」を区別して表示。各方式が評価できる範囲を短く説明する。
- API エラーや未実施を点数に変換しない。評価成功・失敗・未評価を別状態で持ち、比較する候補間で評価条件を揃える。
- スコアが高くても読み誤りの強制判定が残る候補は、自動採用しない。採用しなかった場合の report の final は実際の採用音声の評価と一致させる。
- 改善提案は元本文との差分として示す。固有名詞や意味の変更はユーザーが確認してから採用する。
- 用語の読み辞書を制作単位で保存。元の表記を保持し、合成用の読みだけ変更できるようにする。
- 対応モデルのメタデータと実際のリクエスト形式を確認し、固定モデル一覧への依存を減らす。利用モデルの選定と最新仕様確認は実装時に行う。
- 外部送信される台本・生成音声を操作時に分かるように表示。キーは原則サーバー環境変数またはセッション入力とし、既存 localStorage 保存の解除導線を用意する。
- 外部評価は回数上限・明示的な再試行・音声ハッシュとモデル／評価プロンプト版によるキャッシュを持たせる。

完了条件:

- API 障害でも合成済み音声を利用でき、評価失敗が低品質として誤表示されない。
- 旧版の評価結果が新版の本文・音声へ適用されない。
- 固有名詞、数字、英字、長文、間・強調を含む代表20例程度を固定し、ASR 指標と実際の聞き比べで改善率・悪化率を記録する。
- 自動採用の範囲は上記の実測で決定し、スコア上昇だけで自然さを保証した扱いにしない。

## フェーズ 4 — 待ち時間と納品作業を減らす

優先度 P2。概算 2〜3 人日。フェーズ 1 の実行管理に依存。

実施内容:

- モデル読み込み・生成・評価・結合を別々に計時し、CPU / MPS / CUDA の利用可能な実機で基準値を取る。
- 単一推論ワーカー内で同じモデル・デバイスのインスタンスを再利用し、切替時とメモリ不足時の解放を明示する。ASR と TTS の同時常駐も計測して判断する。
- 経過時間、完了件数、直近実測からの残り時間の目安を表示。初回ダウンロード・モデル読み込み・生成待ちを区別する。
- 参照音声の長さ・無音・クリップ・チャンネルを事前確認し、元ファイルを保存した上で必要な形式へ変換する。
- 変更がない場合は全体 WAV を再結合しない。結合結果は一時ファイルへ出力してから切り替える。
- WAV と、章別／セグメント別音声・台本・生成条件を含む ZIP を書き出す。音量調整は任意とし、クリップとセグメント間の音量差を検証する。
- 初回セットアップ、短い動作確認、失敗からの復帰を README と画面上で案内する。

完了条件:

- 同一モデルの連続再生成で、モデルの再ロードが発生しないことをログで確認できる。
- 20分相当の台本で生成・中断復帰・連続試聴・書き出しを通して確認する。速度の数値目標は最初の実機計測後に決める。
- 書き出した全体音声が採用済みセグメントと一致し、破損・欠落なく最後まで再生できる。

## 実装の分け方

順序は 0 → 1 → 2 → 3 → 4。単独開発で合計 **12〜20 人日程度の初期見積もり**。実モデルの待ち時間・音質調整、対象 OS の追加、未知の依存関係不具合で変動する。最初の実用リリース（0〜2）は 7〜12 人日程度。暦日や性能を保証する見積もりではない。

変更は以下の単位でレビュー可能にする。

1. 例外処理・入力反映・編集保持の修正と回帰確認。
2. 保存形式・版管理・既存 run の取り込み。
3. キュー・中断・再開と制作一覧。
4. 分割プレビュー・試聴・セグメント編集。
5. 比較・採用・復元と全体再生。
6. 評価状態・候補採用条件・読み辞書。
7. モデル再利用・計測・出力の改善。

API 層から制作サービスを切り出し、CLI と Web が同じ生成・採用・結合処理を呼ぶ。永続化と推論実行は別責務にする。manifest は互換性のある書き出し形式として残し、スキーマ版を付ける。既存の未コミット変更を確認しながら小さく進める。

## 検証方針とリリース判定

- パーサー: 日本語の長文、句点なし、SSML の休止・強調・sub、壊れた XML。
- 保存と実行: 例外注入、中断、二重要求、古い版の結果、既存データ取り込み。軽量な偽の合成器で再現性を確保する。
- UI: 取り込み後の編集反映、ポーリング中の入力保持、再読み込み復元、比較・採用・元に戻すをブラウザで確認する。
- 実機: 短い代表例を変更時に確認し、リリース前に長い台本を1本通す。音質は試聴で評価し、自動指標だけで判定しない。
- 最小 CI: 構文・lint と重要な回帰テストを実行。通常 CI に大規模モデル取得や有料 API 呼び出しを必要としない構成にする。

実用リリースの判定は、編集消失なし、失敗時の既存成果物保持、再起動後の再開、元に戻せる部分修正、採用内容と一致する書き出しの5点を満たすこと。見た目の統一はこの制作動線に沿って行う。
